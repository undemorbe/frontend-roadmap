Код написан — пора показать его миру. Эта станция о том, что происходит при `npm run build`, как проверить сборку и где бесплатно опубликовать сайт.

## Что делает vite build

```bash
npm run build
```

Vite собирает проект в папку **`dist`**:

```text
dist/
├── index.html
├── favicon.ico            ← из public/ как есть
└── assets/
    ├── index-B4x9kQ2a.js  ← весь JS, минифицированный
    ├── index-Cm8zLk1p.css ← весь CSS
    └── logo-DfT3a8Qe.svg  ← картинки из src/assets
```

Что происходит при сборке:

- **бандлинг** — сотни модулей склеиваются в несколько файлов, чтобы браузер делал меньше запросов;
- **минификация** — удаляются пробелы и комментарии, имена переменных сокращаются;
- **tree-shaking** — неиспользуемый код («мёртвые» экспорты) выбрасывается;
- **хэши в именах** (`index-B4x9kQ2a.js`) — при изменении файла меняется имя, и браузер точно скачает новую версию, а неизменённые файлы можно кэшировать навсегда;
- **разбиение кода** — динамические `import()` (например, ленивые страницы роутера) выносятся в отдельные чанки.

## Проверка сборки

Папку `dist` нельзя просто открыть двойным кликом — модули не работают по протоколу `file://`. Для локальной проверки есть:

```bash
npm run preview   # статический сервер для dist на http://localhost:4173
```

> [!tip] Совет
> Всегда проверяйте `preview` перед публикацией: ошибки путей (`base`), забытые переменные окружения и проблемы с роутингом видны только в собранной версии.

## base: где будет жить сайт

Если сайт открывается не с корня домена, а из подпапки (`user.github.io/my-app/`), укажите `base`, иначе пути к файлам `assets/` будут неверными:

```js
export default defineConfig({
  base: '/my-app/',
})
```

Значение `base: './'` делает все пути относительными — сборку можно положить в любую папку.

## Где опубликовать

Собранный фронтенд — это **статические файлы**. Их может раздавать любой веб-сервер или специальный хостинг:

| Хостинг | Как |
|---|---|
| **GitHub Pages** | Бесплатно для публичных репозиториев, деплой через GitHub Actions |
| **Netlify** / **Vercel** | Подключаете репозиторий — каждый `git push` автоматически собирается и публикуется |
| **Cloudflare Pages** | То же, с быстрой CDN |
| Свой сервер | Копируете `dist` на сервер с nginx |

Для Netlify / Vercel обычно достаточно указать:

- команда сборки: `npm run build`;
- папка публикации: `dist`.

## SPA и маршрутизация

Приложение с Vue Router в режиме `createWebHistory` имеет адреса вида `/tasks/42`. Но на сервере нет файла `tasks/42` — при обновлении страницы будет 404. Решения:

- настроить сервер отдавать `index.html` на все пути (на Netlify — файл `public/_redirects` со строкой `/* /index.html 200`);
- или использовать `createWebHashHistory` — адреса вида `/#/tasks/42` работают на любом хостинге (так сделан этот учебник).

## Автодеплой с GitHub Actions

GitHub Actions — бесплатная автоматизация: при каждом push в `main` сервер GitHub выполняет ваши команды. Файл `.github/workflows/deploy.yml` для GitHub Pages:

```yaml
name: Deploy
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: github-pages
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
      - uses: actions/deploy-pages@v4
```

Обратите внимание на `npm ci` вместо `npm install`: он ставит строго по `package-lock.json` — сборка воспроизводима.

## Чек-лист перед публикацией

1. `npm run build` проходит без ошибок и предупреждений.
2. `npm run preview` — сайт работает, все страницы открываются.
3. Указан правильный `base`.
4. Переменные `.env.production` заданы (или указаны в настройках хостинга).
5. В `<head>` есть `title`, `description`, favicon.
6. Проверьте сайт в Lighthouse (DevTools → Lighthouse): производительность и доступность.
